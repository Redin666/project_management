## Критерии отбора

Use Case считается кандидатом на исключение, если одновременно:

1. **Низкая или средняя критичность для MVP** — без него система всё ещё выполняет основную задачу: зафиксировать находки пентеста с доказательствами и выдать заказчику отчёт.
2. **Заметный вклад в размер или трудоёмкость** хотя бы по одному из трёх методов.
3. **Функцию можно заменить** более простым механизмом из оставшихся UC или перенести в следующую версию без потери данных.

Отдельно рассматривается **упрощение** функций с высокой критичностью: они остаются в MVP, но в сокращённом объёме.

## Кандидаты на исключение

### UC-11 — Повторная проверка (re-test)

- **Вклад:** 6 CFP (11,3%, второй по размеру), вес UUCW 10, 8 ч (11,8%).
- **Почему не критичен для MVP:** re-test выполняется во втором цикле работ, после того как заказчик устранил уязвимости. Первая версия системы ценна уже на этапе первичного тестирования и отчёта.
- **Чем заменяется:** пентестер меняет статус находки (UC-04, например «исправлено — подтверждено») и прикладывает доказательство проверки (UC-05). Теряется отдельная история результатов повторных проверок; это и есть основная функциональность, переносимая в следующую версию.
- **Риск:** без отдельной сущности re-test нельзя видеть историю нескольких повторных проверок одной находки. Для MVP приемлемо, если статус меняется только с приложением доказательства.

### UC-10 — Комментарий представителя заказчика

- **Вклад:** 4 CFP, вес UUCW 5, 3 ч. Дополнительно: это **единственный** UC актора «Представитель заказчика», поэтому вместе с ним из UCP уходит актор (UAW −3).
- **Почему не критичен:** обмен с заказчиком в MVP идёт через отчёт; обсуждение находок может вестись вне системы.
- **Эффект шире, чем видно в размере:** исчезает внешний пользователь системы. Не нужно выдавать заказчику доступ к находкам, разграничивать видимость результатов между заказчиками и защищать внешний вход. Для системы, хранящей описания уязвимостей и доказательства, это заметно снижает требования безопасности (T11). В расчётах ниже TCF **не пересчитывался** — это дополнительный, не учтённый резерв снижения.

### UC-09 — Экспорт отчёта

- **Вклад:** 3 CFP, вес UUCW 5, 5 ч.
- **Почему не критичен:** в MVP достаточно, чтобы UC-08 сразу формировал отчёт в одном формате. Выбор из нескольких форматов и экспорт сохранённых версий — расширение.
- **Условие:** UC-08 должен отдавать файл, иначе исключение UC-09 оставит пользователя без результата.

### UC-06 — Назначение ответственного (дополнительный кандидат)

- **Вклад:** 5 CFP (столько же, сколько регистрация уязвимости), вес UUCW 5, 3 ч.
- **Почему не критичен:** в небольшой команде пентестеров ответственный может вестись обычным полем находки при редактировании (UC-04) без отдельного процесса и проверки доступа.
- **Почему только во втором сценарии:** экономия по экспертной оценке мала (3 ч). В COSMIC вклад заметен за счёт двух чтений, но, как показано в P3-06, логика процесса простая. Исключение имеет смысл только при жёстком ограничении срока.

### Упрощения без исключения

- **UC-08 «Сформировать отчёт»** — самый тяжёлый UC во всех методах (7 CFP, 13 ч, 19,1% экспертной оценки), но это **итоговый продукт пентеста** — исключать нельзя. Предлагается один фиксированный шаблон без хранения версий и без настраиваемых параметров. Альтернативный сценарий «отчёт по выбранным статусам/серьёзностям» переносится в следующую версию.
- **UC-07 «Найти и отфильтровать»** — список находок проекта с сортировкой по серьёзности и статусу вместо комбинированных фильтров и текстового поиска.

Эффект упрощений в CFP и UCP не выражается: число движений данных и транзакций почти не меняется, снижается трудоёмкость внутри процесса. Поэтому в сценариях ниже они **не учитываются** — это дополнительный запас.

## Итоговые выводы Фазы 3

1. **Масштаб.** MVP системы управления результатами пентеста — небольшая система: 12 Use Cases, 4 актора, 53 CFP, 100,901 UCP, без внешних интеграций.
2. **Трудоёмкость.** Методы согласны в структуре работ и расходятся в абсолютной трудоёмкости почти в 30 раз: 68 чел.-ч по экспертной оценке (только реализация функционального ядра) против 2018 чел.-ч по UCP (полный цикл, 20 ч/UCP; диапазон 1514–2825). Базой планирования принята UCP-оценка (P3-06).
3. **Ресурсоёмкие функции.** Отчётность (UC-08, UC-09) и жизненный цикл находки (UC-03, UC-04, UC-11) дают основную часть объёма.
4. **Команда, компетенции, срок.** ⏳ По результатам P3-07.
5. **Сокращение функциональности.** Рекомендуется вывести из MVP повторную проверку (UC-11), комментарии заказчика (UC-10) и отдельный экспорт отчёта (UC-09), а формирование отчёта и поиск упростить. Это снижает объём примерно на 22–25% и убирает внешнего пользователя системы. ⏳ Итоговая рекомендация по сценарию — после сопоставления со сроком P3-07.

Для Excel требуется `openpyxl`. Перед запуском нужно выполнить `python3 compare.py` в каталоге `comparison/`.
