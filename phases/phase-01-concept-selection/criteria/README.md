# Критерии оценки концепций проекта

## Назначение

В Фазе 1 четыре альтернативы [A1–A4](../concepts/README.md) сравниваются по **единому набору из семи критериев**. Критерии относятся к разным сторонам проекта и позволяют учитывать как преимущества концепции (benefit), так и её затраты и ограничения (cost).

Критерии предназначены для экспертных оценок, последующего нечёткого коллективного TOPSIS и коллективного МАИ. Фактические оценки и веса будут определены участниками отдельно; данный документ их не подменяет.

## Перечень критериев

| Код | Критерий | Тип | Что оцениваем |
|---|---|---|---|
| **K1** | Практическая значимость | **Benefit (max)** | Насколько проект решает реальную и востребованную задачу информационной безопасности; насколько полезен результат предполагаемым пользователям. |
| **K2** | Функциональная содержательность | **Benefit (max)** | Насколько концепция позволяет реализовать связный, полезный набор основных пользовательских сценариев и законченный рабочий процесс. Не поощряется количество функций само по себе. |
| **K3** | Потенциал интеграции и развития | **Benefit (max)** | Насколько просто расширять функциональность и добавлять **необязательные для MVP** интеграции без существенной переработки архитектуры. |
| **K4** | Демонстрационная и исследовательская ценность | **Benefit (max)** | Насколько убедительно можно продемонстрировать работу системы, воспроизвести сценарии, проверить результат и оценить его по понятным показателям. |
| **K5** | Трудоёмкость реализации MVP | **Cost (min)** | Сколько усилий команды потребует разработка минимально работоспособной версии: проектирование, реализация и тестирование. |
| **K6** | Зависимость MVP от внешних ресурсов | **Cost (min)** | Насколько для **базовой работы MVP** необходимы внешние сервисы, закрытые данные, специфическое оборудование, учётные записи или разрешения на доступ. |
| **K7** | Сложность эксплуатации и сопровождения MVP | **Cost (min)** | Насколько трудоёмко после создания MVP обеспечивать развёртывание, конфигурацию, устойчивую работу, диагностику и обслуживание. |

**Benefit:** большее значение предпочтительнее. **Cost:** меньшее значение предпочтительнее.

Обобщённая «реализуемость» из первоначального предложения уточнена: трудозатраты на создание входят в K5, внешние зависимости — в K6, дальнейшая эксплуатация — в K7. Это позволяет не оценивать одни и те же сложности несколько раз.

## Единая шкала оценки альтернатив

Каждый эксперт оценивает **каждую из четырёх альтернатив по каждому критерию** целым числом от **0 до 10**. У всех концепций одинаковые определения критериев и границы шкалы.

| Критерий | 0 баллов | 5 баллов | 10 баллов |
|---|---|---|---|
| **K1 — значимость (benefit)** | Практическая задача не прослеживается | Полезно для узкой группы пользователей | Решает очевидную и востребованную задачу с измеримой пользой |
| **K2 — функции (benefit)** | Нет связного полезного сценария | Реализуется один полноценный основной процесс | Покрываются основные типовые сценарии и их логические связи |
| **K3 — развитие (benefit)** | Расширение требует фактической переделки | Возможны отдельные доработки/интеграции | Чёткие точки расширения и несколько реалистичных интеграций |
| **K4 — демонстрация (benefit)** | Результат трудно показать и проверить | Есть воспроизводимая демонстрация основного сценария | Есть воспроизводимые сценарии, тесты и понятные показатели результата |
| **K5 — разработка (cost)** | MVP требует минимальных усилий | MVP посилен команде, но содержит заметный объём работ | Объём работ для MVP крайне велик относительно возможностей команды |
| **K6 — внешние зависимости (cost)** | MVP автономен, достаточно открытых/тестовых данных | Нужна ограниченная внешняя настройка или доступ | MVP практически невозможен без недоступных данных/сервисов/оборудования |
| **K7 — сопровождение (cost)** | Достаточно простого локального развёртывания | Нужны регулярные настройки, обслуживание или мониторинг | Эксплуатация требует существенно сложной инфраструктуры и постоянного сопровождения |

Промежуточные баллы **1–4 и 6–9** соответствуют промежуточной степени выраженности признака. Важна **сопоставимость** четырёх концепций, а не ложная точность оценивания.

Для benefit **10 означает лучший результат**, для cost **10 означает наибольшую проблему или затраты**. Поэтому нельзя применять правило «10 — лучше» ко всем критериям одновременно.

## Разграничение критериев

- **K1 ≠ K2:** K1 измеряет полезность решаемой задачи, K2 — содержательность предлагаемого функционального решения.
- **K2 ≠ K4:** K2 относится к работе системы для пользователя, K4 — к проверяемости результата и качеству демонстрации.
- **K3 ≠ K6:** K3 оценивает возможности *будущих необязательных* интеграций, K6 — *обязательные* внешние зависимости уже для MVP.
- **K5 ≠ K7:** K5 касается единовременной разработки MVP, K7 — его последующей эксплуатации.
- **K5 ≠ K6:** K5 оценивает объём работ команды, K6 — потребность во внешних ресурсах/доступах независимо от трудозатрат.

## Правила экспертного оценивания

1. Каждый участник отдельно оценивает **A1, A2, A3, A4** по K1–K7 и оценивает **важность** каждого критерия (0 — не важен, 10 — максимально важен). Важность критерия не меняет направления benefit/cost.
2. Для неопределённых оценок фиксируются три сценария: **пессимистичный, ожидаемый, оптимистичный**. Для benefit пессимистичный балл не больше ожидаемого, а оптимистичный не меньше. Для cost **наоборот**: пессимистичный отражает *большие* затраты, оптимистичный — *меньшие*.
3. При записи треугольного нечёткого числа для TOPSIS его компоненты располагаются **по возрастанию числового значения** `(l, m, u)`. Поэтому для cost это численно `(оптимистичный, ожидаемый, пессимистичный)`, несмотря на смысловые названия сценариев. Метки сценариев сохраняются в исходной форме.
4. В TOPSIS K1–K4 рассматриваются как критерии **максимизации**, K5–K7 — **минимизации**. Тип критерия явно учитывается при поиске идеального и антиидеального решений.
5. В коллективном МАИ при попарном сравнении альтернатив по K5–K7 **предпочтение отдаётся меньшим затратам/ограничениям**. Оценки для метода МАИ собираются отдельно в его собственном формате.
6. После получения оценок команда согласует веса, проверяет расчёты обоими методами и сравнивает ранжирования. В данном документе **нет заранее назначенных весов или победителя**.
